# LibreChat Data Entry Agent – Design Assumptions

Status: agreed assumptions, ready for implementation planning. Preliminary feasibility
review against the actual repo done 2026-09-28 (§12) — implementation paused, resuming
in a few days.
Audience: implementation agent with access to the repo, the database schema and the n8n instance.

Items marked **VERIFY** must be checked against the actual code/schema before implementing. Items marked **OPEN** are undecided – ask the team, do not guess.

## 1. Goal

A team of 6 people wants to enter data into the company database faster than through manual NocoDB forms. The agent, available in LibreChat, turns unstructured input (emails, notes, transcripts, dictation) into structured records, shows a preview, asks for confirmation and only then writes to the database.

The agent is an input accelerator, not a general database assistant.

## 2. Environment

- Single VPS, self-hosted: PostgreSQL, n8n, NocoDB, LibreChat.
- LLM access: OpenRouter, most likely a single provider in bring-your-own-key mode. Exact model is **OPEN** – must support reliable tool calling; choose by testing on the scenarios in section 10.
- Table structure is created and changed in NocoDB. 30+ tables exist.
- Existing, out of scope for changes: n8n flow generating offers as PPTX via a custom generic template service filling placeholders with DB data.
- Stay platform-agnostic: no dependency on Google or Microsoft office tooling, no dependency on a specific LLM vendor.

## 3. Users and permissions

- 6 users, identical permissions to all tables. No role model needed.
- User identity is still required for the audit trail (section 7).

## 4. Scope

In scope – three business processes:

1. **Offer inquiries** – registering an incoming request for an offer.
2. **Discovery call notes** – input is mixed: transcripts, own notes, dictation. The DB already has dedicated fields for notes/transcripts (**VERIFY** which ones).
3. **Progress reports** – e.g. a course participant's report after N hours (levels at start/end, communication situations with 1–5 ratings, goals achieved, progress, areas for further work, engagement, recommendation).

Operations: INSERT, UPDATE, read/search.

Out of scope:
- DELETE – never exposed to the agent.
- Generic "find any table and write to it" behaviour. With 30+ tables this is the main source of wrong writes.
- Changes to the existing document (PPTX) generation.

## 5. Architecture

```
LibreChat agent
   │  MCP (streamable HTTP), user identity in headers
   ▼
n8n MCP Server Trigger
   │  one sub-workflow per tool
   ▼
Tool workflows (validation, normalization, preview/confirm, logging)
   ▼
PostgreSQL (tables managed in NocoDB)
```

Decisions:
- Tools are built as n8n workflows. MCP is only the transport between LibreChat and n8n.
- Why MCP instead of LibreChat Actions (OpenAPI): tool list is discovered automatically (no second spec to maintain), and LibreChat supports user placeholders in MCP headers, which the audit trail needs. Whether Actions can pass user identity was not verified.

**DECIDED – write path: NocoDB API.** No direct SQL writes from the tools.
- Consequence: the NocoDB API has no cross-table transactions. For multi-table writes, design an explicit order and compensation (rollback of already created records) in the workflow, so section 7 point 4 is met.
- **VERIFY** whether tables live in a NocoDB-managed base or an external Postgres data source – this affects table/column names used by read tools.

## 6. Tool catalog

### Read tools (shared)

| Tool | Purpose |
|---|---|
| `get_catalog` | Curated, compact description of the tables relevant to the three processes, read live from NocoDB metadata so it never drifts from the schema. Not a raw dump of all 30+ tables. |
| `get_allowed_values(table, field)` | Allowed values of single/multi select fields. The agent must pick from these, never free-type. |
| `find_client` / `find_contact` | Fuzzy search by name (and other identifiers if the schema has them) to avoid duplicates. Returns candidates with IDs. |
| `find_open_items(client_id)` | Open inquiries, discovery calls, courses of a client – used to link new records correctly. |

Exact list of lookup tools depends on the schema (**VERIFY** e.g. trainers, participants, courses).

### Write tools (one per process, fixed schema)

| Tool | Notes |
|---|---|
| `create_inquiry` / `update_inquiry` | |
| `save_discovery_notes` / `update_discovery_notes` | Linked to an inquiry and/or client. Stores raw input (transcript/notes) plus extracted structured fields. |
| `create_progress_report` / `update_progress_report` | Sections generated by the LLM (e.g. progress description, path to next level) are stored with a `draft` status for human approval. **VERIFY** whether a status field exists; if not, propose one. |

Update tools accept only an explicit whitelist of editable fields per process. No generic update tool.

## 7. Write tool contract (applies to every write tool)

1. **Two modes via `confirm` parameter.**
   - `confirm=false` → no write. Returns a preview: normalized data, resolved IDs of linked records, missing required fields, validation errors.
   - `confirm=true` → performs the write. Must be rejected if the payload differs from the last previewed one (or re-validate fully).
   - Confirmation is therefore enforced by the workflow, not by the model's discipline.
2. **Idempotency key** – e.g. conversation ID + hash of payload. A retried call must not create a duplicate.
3. **Validation in the workflow**, not only in the prompt: required fields, types, allowed select values, existence of referenced IDs.
4. **Multi-table writes are atomic** – all or nothing.
5. **Every successful write ends with an entry in `activities`**: who (user email/ID), when, tool, affected tables and record IDs, short summary, conversation ID. **VERIFY** whether `activities` exists and its columns; if not, propose a schema.
6. Errors are returned to the agent in a form it can explain to the user in plain language.

### User identity

LibreChat forwards user data to MCP servers via header placeholders, e.g. `{{LIBRECHAT_USER_EMAIL}}`, `{{LIBRECHAT_USER_ID}}`, and for YAML-defined servers request-scoped `{{LIBRECHAT_BODY_*}}` values such as the conversation ID. The n8n workflows read these headers for logging and idempotency.

Caveat: a bug was reported (July 2026) where user placeholders are not resolved when agents are called through LibreChat's Agents API; the interactive chat UI resolves them. The team uses the chat UI. **VERIFY** on the installed LibreChat version that headers arrive resolved.

## 8. Audit trail

- Agent writes: covered by `activities` (section 7).
- **DECIDED:** manual edits made directly in NocoDB are not logged. No PostgreSQL audit triggers.

## 9. Agent behaviour (system prompt principles)

- Talks to users in Polish.
- Identify which of the three processes the user means; if unclear, ask.
- Extract data from the conversation/attachments into the tool's input schema.
- Resolve references (client, contact, related inquiry) with read tools. Never invent IDs. If several candidates match, ask the user to choose.
- Use `get_allowed_values` for select fields.
- Ask for missing required fields. Do not guess.
- Call the write tool with `confirm=false`, present a short, readable summary, wait for explicit confirmation, then call with `confirm=true`.
- Clearly mark which content was generated by the model (it goes in as `draft`).
- Keep token usage low: the model produces JSON only; documents are rendered by existing services.

## 10. Implementation order and acceptance

1. Read tools + `get_catalog` + identity headers + `activities` logging.
2. `save_discovery_notes` – highest value (most unstructured input).
3. `create_inquiry` / `update_inquiry`.
4. `create_progress_report` / `update_progress_report`.

Acceptance scenarios for each write tool (prepare real examples with the team):
- Happy path: complete input → preview → confirm → correct records + `activities` entry.
- Missing required field → agent asks, does not write.
- Ambiguous client name → agent offers candidates, does not create a duplicate.
- Value not in allowed select options → agent picks a valid option or asks.
- User declines at preview → nothing written.
- Retried confirmed call → no duplicate.
- Schema change in NocoDB → tool fails loudly, no silent partial write.

## 11. Open items summary

- NocoDB-managed base vs external data source (section 5).
- Multi-table write order and compensation strategy on NocoDB API (section 5).
- LLM model choice on OpenRouter (section 2).
- Existence and schema of `activities` and of a draft/status field for progress reports.

**Answers to VERIFY items above:**

- §4 discovery call notes fields — **answered**. `meetings` already has
  `transcript`, `notes`, plus AI-extracted structured fields (`goals`,
  `challenges`, `participant_types`, `business_context`,
  `communication_situations`, `ai_status`). See
  `docs/archive/fable/nocodb_crm_schema_v3.md` §2 and the live dump in
  `docs/archive/fable/schema_map.json`.
- §7.5 `activities` table — **exists live**, fields: `flow`, `type`
  (SingleSelect), `summary`, `payload` (LongText/JSON), `triggered_by`
  (SingleLineText), links to `leads`/`meetings`/`tasks`. Close match for the
  audit-trail contract, but **`triggered_by` today just holds a literal
  string** like `"user"` or a flow name (see `W9_offer_package_texts.json`'s
  "Log activity" node) — not a real per-user identity. Needs a new field, or
  repurposing this one, to hold the actual LibreChat user email; conversation
  id can live inside `payload`.
- §11 progress-report draft/status field — **no dedicated table exists at
  all** for the progress-report process. Genuinely greenfield: needs a new
  NocoDB table, though the repo already has a reusable `status` convention
  for exactly this (draft → review → accepted), see
  `.claude/skills/n8n-flow/SKILL.md` §3.
- §5 write path via NocoDB API — **already the established convention**, not
  just this design's choice: `.ai/rules/common.md` §1 mandates the native
  `n8n-nodes-base.nocoDb` node (never raw SQL/httpRequest) for all CRM
  reads/writes in this repo already.
- §5/§11 multi-table write order + compensation — **de-risked by existing
  workflows**. `W4v2_intake_matching.json` and `W5_company_dedup.json`
  already implement fuzzy lead/company matching (including an LLM-based
  tier) plus an ordered create → link → log-activity sequence. This is
  effectively a working prototype for `find_client`/`find_contact` and for
  "no real DB transactions, just a careful write order."
- §2 LLM model choice — still open, but low-risk: LibreChat and n8n already
  share one OpenRouter key, so no new provider/credential plumbing is
  needed, only model selection and testing per §10.
- §7 user-identity headers — the July-2026-reported LibreChat bug is
  **confirmed real upstream**: GitHub issue `danny-avila/LibreChat#14479`
  (`{{LIBRECHAT_USER_EMAIL}}`-style placeholders resolve in the interactive
  chat UI but not via the Agents API). A fix PR exists (`#13626`, "Resolve
  MCP Runtime User and Request Placeholders"), but **it's unverified whether
  it landed before this repo's pinned LibreChat `v0.8.7`**
  (`fragments/librechat-compose.yml`). Since the team only uses the
  interactive chat UI (not the Agents API), this is likely fine, but should
  be spot-checked before relying on header-based identity for the audit
  trail.
- n8n MCP Server Trigger support — confirmed available. This repo pins
  `n8n:2.30.7` (`fragments/n8n-compose.yml`); the native MCP Server Trigger
  node has existed since n8n v1.88 (April 2025).

**New finding, not covered by any existing VERIFY/OPEN item — needs a
decision before implementation starts:**

- `docs/librechat.md` documents a **deliberate, existing decision** that
  LibreChat is isolated from the CRM: *"Zero integracji z danymi CRM w
  Postgresie — to świadomie osobny byt"* ("Zero integration with CRM data in
  Postgres — this is a deliberately separate entity"). LibreChat's RAM
  budget in `.ai/PRD.md` §1.1 was sized assuming that isolation (no RAG
  API/pgvector/Meilisearch in scope). This agent's architecture (§5)
  reverses that decision by wiring LibreChat → n8n MCP → NocoDB/CRM. Needs
  an explicit decision to update that doc, not just an implementation detail
  to slide past.

itself hasn't happened yet as of 2026-09-26 (still UAT on mock data) — this
agent would compete for priority with finishing that. The VPS also has an
open support ticket for a CPU host-misconfiguration; adding an active
conversational agent plus more n8n tool-call traffic is extra load worth
watching, though RAM headroom was healthy as of the last check (2026-07-18).
